## What changed

| Change | Files | Kept |
| --- | --- | --- |
| **Packed aggregates (P1).** A flush writes each bucket (kind, day, build, layout, mode, and the layer for cells) as one JSON row in `city_packs`, not one row per key. A bucket's small packs merge in one transaction once 16 pile up; a pack is at most 256 KB. The per-key tables are read beside the packs. | `src/worker/city/CityStore.ts` | Every count, in the same API totals. The flush interval (60 s) and its loss window are unchanged. Per-key rows from before stay where they are. |
| **One transaction per flush.** Events and packs commit together. A failed commit writes nothing, and the recorder (which clears its buffers only after the commit) retries it whole. | `CityStore.commit`, `src/worker/city/CityRecorder.ts` | No half-written flush, and nothing counted twice. |
| **Daily event pruning (P2, reads).** `DELETE FROM city_events WHERE day < ?` runs at an instance's first flush and when the cut-off day moves, not every 60 s. | `CityStore.pruneEvents` | The same rows go. Retention is 30 days or longer, never shorter. |
| **Unchanged room state is not rewritten (lossless part of P3).** `room_state` upserts carry `WHERE room_state.value IS NOT excluded.value`. | `src/worker/GameRoom.ts` | The stored values are identical, so the restore point is unchanged. Checkpoint cadence is not changed. |
| **Rollback mode.** `CITY_AGGREGATES=rows` writes per key again. `POST /api/city/v1/unpack[?id=]` (bearer `CITY_TOKEN`) moves one room's packs into its per-key tables, a batch per call in one transaction. `scripts/unpack-city-aggregates.mjs` drains every GameRoom object listed by the Cloudflare API. `scripts/deploy.mjs` passes the variable. | `CityStore.unpackBatch`, `GameRoom.cityUnpack`, `src/worker/city/cityApi.ts`, `scripts/unpack-city-aggregates.mjs`, `scripts/deploy.mjs`, `src/worker/env.d.ts` | After the drain, a release from before packing reads every count. |

**Deferred, not built:**

- **Removing `AUTOINCREMENT` from `city_events`.** It needs a table rebuild or rename. A pre-migration build would then read the wrong table, and the change would move recorded history between tables. Tyler's call; see the plan.
- **Slower checkpoints (P3 cadence) and a longer flush window (P4).** Both widen the restore or loss window.
